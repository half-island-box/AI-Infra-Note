

### 先想象这个三维网格

假设你有 8 张 GPU，配置为 `DP=2, PP=2, TP=2`。把它们排成一个 2×2×2 的立方体：

- **TP 维度**：同一个 PP 阶段内，把一层的权重切成 2 份，两张卡各算一半，算完通过 all-reduce 拼回完整结果。
- **PP 维度**：把模型按层切成 2 段，前一段在 stage 0，后一段在 stage 1。stage 0 算完把激活值传给 stage 1 继续算。
- **DP 维度**：整个“PP×TP”组成的模型副本有 2 份，每份吃不同的数据 batch，反向传播后同步梯度。

每个进程在网格里有一个唯一坐标 `(dp_rank, pp_rank, tp_rank)`。比如坐标 `(0, 1, 1)` 的进程，属于第 0 份数据副本、第 1 个流水线阶段、该阶段内第 1 路张量切分。

### 一次前向传播在三维里怎么走

以坐标 `(dp=0, pp=0, tp=0)` 的进程为例：

1. **TP 协作**：它和 `(0, 0, 1)` 的进程一起，各自持有当前层一半的权重，分别计算部分结果，然后做 all-reduce 得到完整输出。TP 组内的通信非常频繁，所以 TP 通常限制在单机内（NVLink 带宽高）。
2. **PP 传递**：stage 0 算完自己那几层后，把激活值发给 stage 1 的对应进程（`(0, 1, 0)` 和 `(0, 1, 1)`）。PP 组间的通信量是激活值大小，比 TP 的 all-reduce 轻，可以跨机。
3. **DP 独立**：`(1, 0, 0)` 那份副本用另一批数据独立跑同样的前向，互不干扰。

### 反向传播时三种并行同时发生

这是 3D 并行最需要理解的地方——**三种通信在不同维度上同时进行，互不冲突**：

- **TP 维度**：反向时同样要在 TP 组内做 all-reduce，同步张量切分产生的梯度。
- **PP 维度**：stage 1 的梯度通过流水线传回 stage 0（反向的激活值传递）。
- **DP 维度**：所有 PP×TP 组合的副本，在各自 DP 组内做梯度 all-reduce，保证两份数据副本的模型参数一致。

关键在于：**每个进程只在自己所属的组内通信**。TP 组是“固定 dp 和 pp，变化 tp”的那条线；PP 组是“固定 dp 和 tp，变化 pp”的那条线；DP 组是“固定 pp 和 tp，变化 dp”的那条线。三条通信线正交，各管各的。

### 为什么要三个维度一起用

- **TP 单独用**：切得太细，all-reduce 通信太频繁，跨机就崩了。所以 TP 一般不超过单机 GPU 数。
- **PP 单独用**：能跨机，但有“流水线气泡”——前面的 stage 在算，后面的在等。需要 micro-batch 填充来缓解。
- **DP 单独用**：每张卡都要存完整模型，大模型放不下。

3D 并行是**各取所长**：TP 解决单层太大放不进一张卡，PP 解决层数太多跨机切分，DP 解决吞吐不够多副本跑数据。三者组合，才能把千亿参数模型铺到几百张卡上。

### 一个容易混淆的点

3D 并行里，**DP 的“数据并行”和纯 DP 不完全一样**。纯 DP 是每张卡一份完整模型；3D 里的 DP 是“每个 PP×TP 组合的模型副本”有 DP 份。所以 DP 组的大小决定了有多少份完整模型副本在并行吃数据，而不是每张卡一份完整模型。

理解了这个网格和三条正交通信线，再看那些 `world_size == dp * pp * tp` 的断言和 `(dp_rank, pp_rank, tp_rank)` 的坐标划分，就顺理成章了。
