## KIVI：Key按通道，Value按Token
### KV误差影响的区别
由 `P = softmax(QK^t/sqrt(d) O = PV` 可知，

**Key的误差可能让模型关注错位置** -> 量化应该在同个通道内进行
**Value的误差按注意力权重加权后影响输出** -> 量化在同个seq内进行

### KIVI的量化思路
[KIVI](https://arxiv.org/abs/2402.02750) 是一种免调参的 2-bit KV Cache 量化算法。
它的出发点是一个观察：
在其研究的模型中，**Key 有明显的通道离群值，Value 没有**。

因此论文**主张 Key 按通道量化、Value 按 Token 量化。**
固定一层、一个请求和一个 KV Head，把 K、V 都看成 T×dT×d 矩阵，
”行 = Token，列 = 通道”的约定：

- **Key Per-channel**：
	固定一个通道，沿连续的若干 Token 分组求量化参数（竖着切）。
	大幅值通道就被单独隔离开，不会拖累其他通道
	
- **Value Per-token**：
	固定一个 Token，沿通道分组求量化参数（横着切）。
	每个Token用自己的范围

### 具体的工作机制
由于 LLM 推理是逐 Token 生成的（流式），Key 的“按通道量化”需要跨 Token 才能完成，无法直接流式追加。
KIVI 为此设计了**分组（Grouped）与残差（Residual）** 分离的流程：

1. **分组部分（Grouped Cache）**：将已经积累到足够数量（一个完整组，例如 32 个 Token）的 Key/Value 进行量化压缩存储。
    
2. **残差部分（Residual Cache）**：对于最新生成、还凑不齐一个完整组的少量 Token，**保留全精度（FP16）** 不进行量化。这保证了最近上下文的高保真度。
    
3. **计算时合并**：在计算注意力分数时，分别从量化后的分组部分和全精度的残差部分读取数据，通过分块矩阵乘法沿token维度拼接，得到合并的计算结果。

## KVQuant：KIVI基础上的各环节优化
KVQuant 相比 KIVI 新增的量化环节，
其机制可以拆解为四个相互配合的设计，**共同目标是在 2-3 bit 的极低位宽下维持模型精度。**

### Pre-RoPE键量化：在旋转“搅乱”分布之前动手
RoPE旋转位置编码，会对不同位置的Key旋转不同角度，
导致原本具有稳定通道幅度的key分布被打散，量化后精度损失明显

**KVQuant采取先量化，后旋转**
	将 Key 向量在应用 RoPE 之前就以低精度存储，
	推理时先反量化恢复近似原始 Key，再实时补上 RoPE。

### 离群值隔离：极少数离群通道/token单独看管
KV Cache 中极少数数值异常大的离群点，
如果和正常值用同一个 scale 量化，会把量化范围撑得过大，
导致大量正常值被压缩到极少的格点上，精度严重损失。

KVQuant 的机制是**动态阈值检测**：
	设定一个离群点阈值，超出阈值的元素不参与常规量化。
	具体操作上，**Key 按通道粒度判定离群，Value 按 Token 粒度判定，**
	确保每种向量在最适合自己的粒度上被“隔离保护”。

### 首token保护：特殊位置特殊对待
大模型存在一种“注意力下沉”现象：
	即使序列第一个 Token 在语义上并不重要，模型仍会给它分配异常高的注意力分数。
	量化这个位置的 KV 的影响比其他位置大得多

KVQuant 直接**保留序列中第 1 个 Token 的 KV Cache 原始精度，不做量化**。
	这是一个简单但有效的保护措施，
	避免了因特殊位置的高敏感度而拖累整体输出质量。

### 非均匀量化：量化间隔跟着数据走
均匀量化使用等间距的整数格点，假设数据在范围内均匀分布。
**但 KV Cache 的实际分布往往集中在某些区间，均匀格点会在稀疏区浪费表示能力。**

KVQuant 引入**按层敏感度加权的非均匀数据类型**：
	通过校准数据推导每层的分布特性，将量化格点放置在更贴合实际数值分位数的位置，
	并用**敏感度权重调整各层对量化误差的容忍度**。
	这意味着不同层可能拥有不同形状的“格点地图”，而非一刀切的等距划分。

#### Fisher信息：量化精度损失风险
KVQuant在LLM进行前向校准时，保存每个权重的Fisher信息

执行非均匀量化NUQ时，采用结合Fisher值的加权 K-means量化，
把每个权重的Fisher值作为聚类权重
**从而得到用权重推倒的非均匀码本**

> 为什么是量化KV，但是统计的Fisher是关于权重？
> **KV是在线推理时动态生成的，离线的校准推理无法统计**
> **并且KV是由这些固定的KV矩阵的权重生成的**

## vLLM的FP8 KV Cache
工程上**更常用的路线是把 KV 存成 FP8：**
	数据量减半，精度压力比 2-bit 小得多，
	也不需要 KIVI 那样的特殊缓存结构。

### 常用格式
`kv_cache_dtype` 的常用取值：

|📊 取值|含义|支持说明（v0.32.0 文档）|
|---|---|---|
|`auto`|与模型数据类型一致|默认值|
|`fp8` / `fp8_e4m3`|E4M3，精度更高|CUDA 11.8+ 与 ROCm|
|`fp8_e5m2`|E5M2，范围更大、精度更低|CUDA 11.8+|

源码里的 `CacheDType` 还列出了 `int8_per_token_head`、`fp8_per_token_head`、`nvfp4` 等更多选项，它们依赖特定的 Attention 后端，使用前要查对应后端的支持情况。另外，DeepSeek-V3.2 等少数模型默认就用 FP8 KV。
### 存储精度不等于计算精度
FP8 KV 首先减少的是存储；
读出来以后，后端可能转回高精度再算，也可能直接在 FP8 域做 Attention。

vLLM 文档注明，**Flash Attention 3 后端配合 FP8 KV 时，Attention 在 FP8 域计算，Query 也会被量化成 FP8**。
所以只看 `kv_cache_dtype` 不能断定整段 Attention 的精度，
要结合 GPU、后端和启动日志一起判断（第 2 章讲过后端选择）
